# DSH 压缩与缓存排查记录

2026-10-04，SuperLcm 0.5.7；本机 DSH 0.2.1-alpha.1。

## 已确认的问题

已有自定义预设声明自己的 `compaction-basic` 和 `tool-result-pruner`，并隔离
`compaction` 服务。原接入检查只检查宿主，没有检查这些预设，所以全局设置
并未覆盖全部智能体。在实际会话里发现多轮 `compaction/prune`，它会替换旧工具
结果；另一次摘要使用预设默认模型，未使用 SuperLcm 控件指定的模型。

更新接入时，现有预设退出独立压缩和裁剪服务，继承宿主 SuperLcm。检查接入
增加预设冲突检测。后来新增的独立压缩预设需要重新管理接入，不能视作自动接管。

DSH 默认摘要请求沿用主会话标识。安装环境中的 OpenCodex 按会话记录最近服务
身份，身份包含模型。相同账号下，主模型与摘要模型交替也会被识别为身份改变，
触发清除出站加密推理内容。使用安装版本的真实函数、固定本地输入复现了这个
过程；独立摘要标识消除了该冲突，无须更换账号。这个机制能解释未提交压缩时
输入减少和前缀缓存丢失，但历史日志没有保存完整出站内容，不能断言每次截图
里的缓存下降都由它造成。

0.5.7 为每个主会话及摘要路线产生独立稳定标识。重启后的真实代理用量记录
确认：两条主会话和各自的后台摘要分别使用四个不同的会话标识。
摘要完成后，顾问主模型的一次输入为 196,093 token，命中缓存 193,152 token；
主线程也连续产生新模型响应及工具调用。后台任务继续分批准备摘要，没有因
摘要请求结束而在主日志插入上下文替换。

## 摘要位置

轨迹按写入时间显示新摘要，实际请求按 `surfaceOp: replace` 重建。重放实际
主线程日志，最新摘要位于上下文第 2 个消息节点：系统提示之后、近期对话之前。
摘要位于轨迹底部不等于位于实际请求末尾。

## 验证范围

`npm run validate`：113 项通过；`npm run test:dsh-runtime`：14 项通过。
包括独立摘要标识、软门槛和硬压力下不提交未完成批次、已有批次不被重复选择、
预设内部压缩冲突、单组件接入、归档及失败保护。

读取真实长会话并在隔离的 DSH 会话中重放，使用本地固定摘要，分 3 批准备，
准备前后原上下文完全一致；模拟跨过 260K 门槛后，只产生一次替换。
这验证提交时机及范围，不评估模型摘要质量，也不验证供应商的缓存策略。

另在临时用户目录安装插件、运行真实 DSH，压缩和归档均回报加载版本 0.5.7；
带压缩服务的测试预设完成迁移并激活，无付费模型调用。生产 DSH 随后已重启，
两条现有会话均恢复新回复及工具调用，所有当前声明的预设检查无压缩冲突。

上线后的真实主线程在 01:54 完成一轮 SuperLcm 提交：`preparedBatchCount=3`，
摘要模型为用户配置的 `gpt-6-luna`，只产生一组提交事件。前一次主请求输入
258,229 token，提交后输入 78,458 token，减少 179,771；下一次输入 78,961，
缓存命中 78,336。旧内容完整保留。这是线上真实模型回执，区别于上述固定摘要重放。

同一会话 01:52:51 还有一次提交前缓存归零。会话在该时刻写入
`request/header`，原因 `change`，新增工具 `v9_review_medium`；模型与推理档位
保持一致，没有压缩替换。工具列表是请求前缀的一部分，这次前缀变化解释了
这次缓存失效。不能把动态安装工具导致的前缀变化归因于后台摘要提交。
